# Как релизить AudioControl Central на GitHub — пошаговый гайд

Что ты получишь в конце: страницу **Releases** в твоём GitHub-репозитории с файлом
`AudioControl-v0.1.0-windows-amd64.exe`, который любой может скачать, запустить —
и всё работает без установки.

Гайд рассчитан на первый релиз с нуля (проект ещё не в git). Повторные релизы —
это просто Этап 5.

---

## Этап 0. Что нужно перед стартом

Проверь, что есть всё перечисленное:

| Что | Как проверить |
|---|---|
| Аккаунт на [github.com](https://github.com) | Залогинься в браузере |
| **git** | `git --version` |
| **Go 1.25+** | `go version` (проект требует go.mod → 1.25.0) |
| **Node.js 18+** | `node --version` |
| **Wails CLI** | `wails version` — если нет: `go install github.com/wailsapp/wails/v2/cmd/wails@v2.15.0` |
| **GitHub CLI `gh`** (опционально, упрощает много шагов) | `gh --version` |

> Wails CLI ставь именно `@v2.15.0` — совпадает с версией фреймворка в `go.mod`.
> Это не каприз: `@latest` может внезапно прийти с несовместимой версией и сломать сборку.

Если установишь `gh` — залогинься: `gh auth login`.

## Этап 1. Мелкие правки в проекте (делаются один раз)

### 1.1. README: замени плейсхолдеры OWNER/REPO

В `README.md` **5 мест** содержат заглушки `OWNER` и `REPO`. Замени их на свой
логин GitHub и имя репозитория:

- строка с бейджем **Release** (~7);
- строка с бейджем **Downloads** (~8);
- ссылка «страница релизов» в разделе **Установка** (~28);
- `git clone https://github.com/OWNER/REPO.git` (~52);
- `cd REPO` (~53).

Пример: логин `ivan` + репозиторий `AudioControl` → `https://github.com/ivan/AudioControl`.

> Это важно сделать до первого коммита: бейджи и ссылки уедут в git в правильном виде,
> и после релиза они сразу заработают.

### 1.2. wails.json: добавь блок `info` и реального автора

Открой `wails.json` и добавь блок **`info`** (после `"author"`). Это метаданные,
которые Windows показывает в «Свойствах файла → Подробнее» и которые попадают
в манифест exe:

```json
"author": {
  "name": "Твоё имя",
  "email": "ты@пример.com"
},
"info": {
  "companyName": "Твоё имя или организация",
  "productName": "AudioControl Central",
  "productVersion": "0.1.0",
  "copyright": "Copyright (c) 2026 Твоё имя",
  "comments": "Global per-process volume hotkeys for Windows"
}
```

> Без блока `info` в свойствах exe окажется мусор от дефолтов Wails
> («Copyright.........»). Версию релиза ты будешь менять только здесь —
> см. Этап 4, шаг 1.

### 1.3. LICENSE: укажи себя как правообладателя

В `LICENSE` замени строку `Copyright (c) 2026 AudioControl Central contributors`
на свой вариант, например: `Copyright (c) 2026 Ivan Petrov`.

### 1.4. (Необязательно) Иконка

В `build/appicon.png` лежит текущая иконка. Если будешь менять — бери квадратный
PNG от 512×512 с прозрачностью и **проверь, как она выглядит в 16×16** (это
размер в системном трее). После замены собери `wails build` — иконка обновится
и в exe, и в трее.

## Этап 2. Git + репозиторий

### 2.1. Инициализируй git и сделай первый коммит

Открой терминал в папке проекта (`E:\Projects\GO_VLM\AudioControl_v3`) и выполни:

```bash
git init
git add -A
git commit -m "Первый коммит: AudioControl Central"
git branch -M main
```

> `git branch -M main` — переименовывает ветку в `main` (правило GitHub по умолчанию).

`git add -A` возьмёт всё, кроме `frontend/node_modules`, `frontend/dist`,
`build/bin` и логов — они уже исключены файлом `.gitignore`.

### 2.2. Создай репозиторий на GitHub

**Вариант А — через `gh` (быстро):**

```bash
gh repo create AudioControl --public --source=. --push
```

**Вариант Б — через браузер:**

1. github.com → кнопка **«+»** (справа сверху) → **New repository**;
2. Repository name: `AudioControl`; Public; **не** отмечай «Add a README» и «.gitignore» (они уже есть);
3. **Create repository**;
4. В появившейся инструкции скопируй и выполни команды для «…or push an existing repository from the command line»:

```bash
git remote add origin https://github.com/ТВОЙ_ЛОГИН/AudioControl.git
git push -u origin main
```

### 2.3. Включи GitHub Actions (если репозиторий приватный)

Если репозиторий **public** — Actions уже работает, этот шаг пропусти.
Если **private**: Settings → Actions → General → раздел «Permissions» →
отметь **Allow all actions and reusable workflows** → Save.

## Этап 3. Проверь, что CI зелёный (до релиза)

Открой в репозитории вкладку **Actions** — там должен появиться workflow **CI**.

Видишь ✅ — отлично. Он прогнал: форматирование Go, сборку, тесты, сборку
фронтенда. Дальше смотри, что **go vet** выделен предупреждением (жёлтый) —
это норма:

> `go vet` находит 4 штатных предупреждения `possible misuse of unsafe.Pointer`
> (обычный Win32-паттерн в `media/gsmtc.go` и `hotkey/listener.go`). Они намеренно
> не роняют CI. Если увидишь предупреждения сверх этих четырёх — вот это уже баг.

Если шаги упали (красный) — жми на упавший шаг, там видно причину. Самые частые
случаи — в таблице «Частые проблемы» внизу.

## Этап 4. Первый релиз `v0.1.0`

### Шаг 1. Подними версию

В `wails.json` поменяй `info.productVersion` на новую версию (без буквы `v`):

```json
"productVersion": "0.1.0"
```

### Шаг 2. Локальные проверки перед релизом

```bash
gofmt -l .      # пустой вывод = ок
go build ./...
go test ./...
```

```bash
cd frontend
npm install
npm run build
cd ..
```

Любая ошибка здесь — это ошибка, которую увидит пользователь. Чини до тега.

### Шаг 3. Закоммить

```bash
git add -A
git commit -m "Release v0.1.0"
```

### Шаг 4. Поставь тег и запушь

Релизный workflow слушает теги вида `v*` — **без буквы `v` релиз не запустится**:

```bash
git tag v0.1.0
git push origin main --tags
```

### Шаг 5. Что произойдёт дальше (само, без твоего участия)

GitHub Actions запустит workflow **Release**, который:

1. ставит Go, Node.js и Wails CLI (версия из `go.mod` + `@v2.15.0`);
2. собирает приложение: `wails build`;
3. переименовывает результат в `AudioControl-v0.1.0-windows-amd64.exe`;
4. создаёт релиз `v0.1.0` с автогенерированным описанием (GitHub соберёт его из коммитов);
5. загружает на него exe.

### Шаг 6. Проверь результат

1. Вкладка **Actions** → workflow **Release** — все шаги ✅.
2. Вкладка **Releases** — увидишь `v0.1.0` и под ним файл `AudioControl-v0.1.0-windows-amd64.exe`.
3. Скачай этот exe и протестируй на Windows:
   - запускается, сворачивается в трей, из трея открывается;
   - хоткеи срабатывают (вкладка «Настройки» → «Диагностика»: комбинации зарегистрированы);
   - автозапуск включается и переживает перезагрузку;
   - «Свойства файла → Подробнее»: версия `0.1.0`, правильные автор и копирайт.
4. Через несколько минут обнови страницу репозитория: бейджи **release** и **downloads**
   в README покажут версию.

Готово — релиз вышел. 🎉

## Этап 5. Все следующие релизы (одна команда-алгоритм)

Для `v0.2.0`, `v1.0.0` и дальше — ровно то же:

1. `wails.json` → `info.productVersion` = новая версия (например `1.0.0`);
2. проверки (`gofmt -l .`, `go build ./...`, `go test ./...`, `npm run build`);
3. `git add -A && git commit -m "Release v<версия>"`;
4. `git tag v<версия> && git push origin main --tags`;
5. Actions → Release зелёный → Releases → скачать и проверить.

Исправление бага за v0.1.0 → выпускай **v0.1.1** (patch-бамп). Ради исправления
перезаписывать старый тег не стоит — история остаётся чище, а пользователям
понятнее. Если очень нужно перезалить файл в уже созданный релиз, выкачай его
на странице Releases → «Edit» → «Replace asset».

## Частые проблемы

| Симптом | Причина → решение |
|---|---|
| Запушил тег — workflow Release не запустился | Тег без `v` → удали и поставь заново: `git tag -d 0.1.0 && git push origin :0.1.0`, затем `git tag v0.1.0 && git push origin v0.1.0` |
| `gh release create` падает с 403 | В workflow уже прописано `permissions: contents: write`; проверь, что Actions включены (§2.3) |
| CI падает на `npm ci` | Локально выполни `npm install` (обновит `frontend/package-lock.json`), закоммить изменённый lock-файл |
| CI падает на `go vet` | Должен быть «жёлтым» (continue-on-error); красный — это новые замечания кроме 4 штатных |
| В свойствах exe старая версия | Забыл поменять `info.productVersion` перед тегом (§4.1) |
| SmartScreen ругается при запуске | Сборка не подписана — это норма. Кнопка «Подробнее» → «Выполнить в любом случае». Про подпись см. ниже |
| Хочу пересобрать релиз заново (не перезаливать файл) | Удали тег локально и на GitHub, поставь заново (команды выше) — workflow запустится повторно |

## Опционально: подпись кода (чтобы SmartScreen помалкивал)

SmartScreen не боится Open Source — он боится неизвестных издателей, а у нас
подписи нет. Честный минимум: ничего не подписывать (README уже объясняет это
пользователю). Если захочешь убрать синий экран:

- нужен **OV- или EV-сертификат** (платный, у CA типа DigiCert/GlobalSign); самоподписанный не помогает;
- подпись ставится после `wails build` через `signtool sign /fd SHA256 ...`;
- шаг подписи можно вписать в `.github/workflows/release.yml` (сертификат
  кладётся в секреты репозитория: Settings → Secrets → Actions).

## Опционально: опубликовать релиз вручную (без CI)

Если Actions отключены или что-то сломалось, а релиз нужен сейчас:

```bash
# собери локально
wails build
Get-Item build/bin/AudioControl.exe     # убедись, что файл на месте

# залей вручную (gh установлен и авторизован)
gh release create v0.1.0 build/bin/AudioControl.exe --generate-notes
```

Для красоты переименуй exe так же, как это делает workflow:
`AudioControl-v0.1.0-windows-amd64.exe` (README обещает именно такое имя файла).
